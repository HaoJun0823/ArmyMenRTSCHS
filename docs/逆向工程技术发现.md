# Army Men RTS 逆向工程技术发现

本文记录《Army Men RTS》Steam 版汉化过程中，通过 IDA Pro 反编译 + 运行时验证得到的引擎事实，
以及据此实现运行时汉化所踩过的坑。

**适用版本**：Steam 版 `amrts.exe`，md5 `a28b3085346fdfe483b0395bdf9bad5f`，
imagebase `0x400000`。所有地址基于此版本，**换 exe 需重新定位**。

文中标注「实测」的内容有字节级或运行时证据；标注「推断」的尚未完全证实。

## 1. DOCB 文本容器

`library\language\english.dat` 不是明文 ini，而是 Pandemic 的二进制字符串树。

### 布局

```
文件 = [44 字节头] + [10 字节间隙] + [blob] + [12 字节尾]
       0x00            0x2C..0x35     0x36      len-12
```

| 字段 | 偏移 | 说明 |
|---|---|---|
| magic | 0x00 | `DOCB` |
| version | 0x04 | u32 = 1 |
| blockCount | 0x08 | u32 = 2（两块声明，见 `sub_4E6300`） |
| 目录项 | 0x0C.. | 2 × 8 字节 |
| **数据区大小** | **0x30** | u32，= `file_len - 52 - 12` |

**`0x30` 是最容易踩的字段**：它描述从 `0x34` 到 `len-12` 的数据区长度。
引擎 `sub_4DB6E0` 按它走目录，若重建的 blob 比原来短而没同步这个值，
就会读到 EOF 之后，报：

```
Failed reading 8 bytes from block file "library\language\english.dat"
```

修法：把 blob 补齐回原始大小，并重写 `0x30`。

### 节点结构

blob 从 `0x36` 开始。`0x34` 处的 u16 是顶层节点数（实测 7）。

```
节点 = type:u8, nameLen:u8, name[nameLen]   // nameLen 已含结尾 NUL
       名字后按 2 字节对齐：advance = (nameLen + 1) & ~1

type=6/0  容器：紧跟 u16 childCount，随后递归 childCount 个子节点
type=4    叶子：紧跟 u16 vlen(= 值字节数 + 2), u16 tag, value[vlen-2]
            值后 advance = (vlen + 1) & ~1 + 2
```

`tag` 是 u16，含义未逆向（疑似值类型标记），**必须原样保留**才能往返无损。

### 查键方式

游戏对路径每一段算 **CRC32**（`sub_4D9A30`，正向 CRC32，恒等 S-box，
多项式 `0x04C11DB7`），在排序索引里二分查找。

**结论：节点名（键）绝不可翻译，只能翻译叶子值。**
这也是翻译工具只替换 value、不动 path 和 tag 的原因。

### 格式来源

来自 IDA 反编译 `sub_4E6180`（由 `sub_4E6300` 加载后循环调用）+ 字节级往返校验
（重新序列化后与原始 34334 字节完全一致，范围 `[0x36, 0x8654)`）。

**1 代源码不含 DOCB 实现**，格式并非来自源码。

## 2. `.fff` 点阵字库

### 文件格式

```
"BORK" | u16 count | u8 metric | 2 字节跳过   => 条目表从偏移 9 开始
```

条目表 `count` × 7 字节：

| 字段 | 类型 | 说明 |
|---|---|---|
| slot | u16 | 字符码 |
| adv | u8 | 步进 |
| l | u8 | 左边界 |
| t | u8 | 上边界 |
| r | u8 | 右边界 |
| b | u8 | 下边界 |

随后是字形数据，每字形 `u8 w, u8 h, w*h 字节`（8 位 alpha）。

**条目表在偏移 9，不是 10。** 写成 10 会让引擎读到整表错位，
表现为字形全零、文字不显示。

### 度量是基线相对的

`l/t/r/b` 不是纹理坐标，而是**相对基线**的布局值：

```
l = 1
r = 1 + w
t = b_ref - h
b = b_ref
```

`b_ref` 从原版字体实测：metric 16 → 13，metric 19 → 18，metric 30 → 29。
（`font_stencil_24_resource.fff` 是 metric 27，另属一组。）

**这一条错了会直接毁掉排版**：早期把 `t/b` 写成字形在页内的像素行号
（如 `t=17, b=20`），文字整体向左下漂移。

### 尺寸约束与打包

- 纹理页固定 **128 × 128**
- 单字形 `w, h <= 100`
- 引擎打包逻辑（实测）：`Source` 从 1 开始，每字形 `Source += w + 1`；
  当 `Source + w + 1 > 127` 换行（`y += 本行最高字形`，`Source = 1`）；
  行高取本行最高字形，溢出则开新页
- UV = `Source / 128` 与 `y / 128`（`0.0078125 = 1/128`）

**按页容量算字形数**：200 字形/页远超 128×128=16384 像素。
实测需求 g0 33,979 px、g1 61,756 px、g2 172,680 px，溢出 2×/3.8×/10×。
正解是**模拟引擎打包算法自动分页**，本项目最终 87 页（11 + 22 + 54）。

### 原版字体自带西里尔

三个原版字体（`font_arial_10` / `font_stencil_14` / `font_stencil_24`）
的 `0x80-0xFF` 槽位共 128 个，其中 `0xC0-0xFF` 这 64 个正是
`АБВГДЕЖЗИЙКЛМНОПРСТУФХЦЧШЩЪЫЬЭЮЯабвгдежзийклмнопрс`。

**这个事实是后面多个 bug 的放大器**：任何被拆成单字节的 GBK 高位字节，
经引擎 `u8` 查表后都会显示成西里尔字母。

## 3. 字体对象与字形查找

### 字形查找 `sub_4A25E0(Font* table, u8 ch)`

```c
count = *(u16*)(table + ch*8 + 0x11C);    // 候选数
array = *(void**)(table + ch*8 + 0x120);  // 条目数组
// 40 字节条目，匹配 *(u16*)entry == ch
```

**索引是 `u8`**，Unicode 码位会被截断。
这是汉化方案的核心约束：**汉字必须重编号到槽位 1..N**，
由我们自己的索引维护 Unicode → (组, 页, 槽位) 映射。

### 字体对象布局

| 偏移 | 内容 |
|---|---|
| object+0 | 名字（0x40 字节） |
| object+68 | hash |
| **object+72** | **= 引擎运行时使用的 glyph table 指针** |
| table+0x11C / +0x120 | 字形候选数 / 条目数组 |
| **table+0x114** | **metric，单个 BYTE** |

对象总大小 `0x97C`。

`metric` 必须是**单字节读取**。`sub_4A26F0` 里是 `v67[69] = *v7`
（`v7` 是 `unsigned __int8*`），写成 `u16` 读会把邻近字节带进来，
导致按 metric 选组时选错字号。

### 运行时字形记录（40 字节）

| 偏移 | 类型 | 内容 |
|---|---|---|
| +0 | u16 | 字符码 |
| +2 | u16 | **advance** |
| +4 | u16 | 纹理页 |
| +8/+12/+16/+20 | u16 | l / t / r / b |
| +24..+39 | float ×4 | u0, v0, u1, v1 |

### `.fff` 加载与文件解析 `sub_4A26F0`

经 `sub_4D94D0`（游戏 VFS）解析路径：

- 路径**含 `\`** → `sub_4D9410` 直接开磁盘文件（UAL 的 `update/` 重定向在此生效）
- 路径**不含 `\`** → `sub_4D8150` 走已注册文件系统链（原版字体在 `base.x` 里这样找到）

传绝对路径会让 `sub_4D94D0` 抛异常（被 catch 成 -1），必须用 VFS 相对路径。

### 多字号分组

游戏同时存在三四个不同行高的字体，用单一字号渲染 CJK 在某个界面必然难看。
做法是**按 metric 分组建多套字体对象**，运行时读当前字体的 `table+0x114`
自动选组：

| 组 | metric | 对应原版字体 | 用途 |
|---|---|---|---|
| g0 | 16 | `font_arial_10.fff` | System / Console / Button |
| g1 | 19 | `font_stencil_14.fff` | Debriefing |
| g2 | 30 | `font_stencil_24.fff` | Movie / Resource |

## 4. 纹理生命周期

**这是「进入 3D 世界后文字变实心方块」的根因所在。**

### 纹理管理器

```c
void* dword_72778C[1000];   // 纹理页指针数组
u16   dword_727788;         // 已分配计数（上限 1000）
```

`sub_4A55A0` 分配一页：计数到 1000 则失败，否则 `*this = 计数++`，
`dword_72778C[*this] = sub_42D160(18)`（前置条件 `sub_4CFAB0(0x168)`）。

### 销毁函数 `sub_4A5A30`

```c
for (i = 0; i < 1000; ++i)
    if (dword_72778C[i]) {
        dword_72778C[i]->vtable[4](dword_72778C[i], 1);   // Release
        dword_72778C[i] = 0;
    }
dword_727788 = 0;
```

**它有且仅有两个调用者，行为完全不同：**

| 调用者 | 销毁后的行为 |
|---|---|
| `sub_4A5AF0` | 遍历已注册字体，逐个 `sub_4A26D0(f + 72)` **重新加载** |
| `sub_4A5940` | **不重新加载字体**，只清空链表（`dword_728744` 等） |

`sub_4A5940` 由 `sub_48D890` 调用，**进入 3D 世界走的是这条**。

**教训**：只 hook `sub_4A5AF0` 是错的——日志显示它从未被触发，
atlas 一直持有失效的纹理 ID，glyph 记录里的 `tex` 指向别人的纹理，
采样出来就是实心方块。

运行时证据：`dword_727788` 读到 13，而字形记录引用的是 24..43，明显越界。

**正解**：hook `sub_4A5A30` 本身，两个调用者都能覆盖；
在**原函数执行前**丢弃 atlas（反正纹理马上要被释放，记录先失效），
下一次绘制时按新的纹理编号惰性重建。

`sub_4A5A30` 序言：
```
56              push esi
57              push edi
BE 8C 77 72 00  mov  esi, 0x72778C
BF E8 03 00 00  mov  edi, 0x3E8        // 1000
8B 0E           mov  ecx, [esi]
85 C9           test ecx, ecx
```
边界 0/1/2/8/14/16，**无 rel32 需要重定位**，hook 安全性高于 `sub_4A5AF0`
（后者第 2 条指令就是 `call rel32`）。

## 5. Inline hook 的正确做法

本项目用 5 字节 `JMP` 覆盖目标，原函数经 trampoline 调用。
**两个必须处理的点，漏一个就是崩溃或静默错乱。**

### 5.1 必须落在指令边界上

早期实现按「opcode 特例表」估长度，列出过 `8B 35`、`8B 86` 之类。
**这种枚举不可能完整**——`mov ebp, esp` 是 `8B EC`，普通 modRM 形式，
没在表里，于是 `sub_4A2C50` 的 hook 直接安装失败：

```
55 8B EC 81 EC AC 00 00 00
^^ ^^^^^ ^^ ^^^^^^^^^^^^^^
1  2     6  sub esp, 0xAC
```

请求 9 字节时，走到 `0x81` 发现 `HasModRM(0x81)` 为 false——
区间写成 `0x84-0x8F` 把 `0x80-0x83`（ALU imm 组）切掉了。

**正解**：写通用 x86 指令长度解码器，覆盖前缀、单/双字节 opcode、
modRM + SIB + disp8/disp32、立即数。关键区间：

| opcode | 有 modRM | 立即数 |
|---|---|---|
| `0x00-0x3F` | 是 | 部分 |
| `0x80-0x8F` | 是 | `0x80/0x82/0x83`→1，`0x81`→4 |
| `0xC6/0xC7` | 是 | 1 / 4 |
| `0xC8-0xCF` | **否**（enter/leave/int/iret） | — |
| `0xD0-0xD3` | 是 | `0xC0/0xC1`→1 |
| `0xF6-0xFF` | 是 | — |

遇到不认识的形式**直接拒绝安装**，而不是猜长度——猜错就是截断指令。

另外，请求 N 字节时要**向上取整到第一个 ≥ N 的边界**，不能向下取：
JMP 补丁固定占 5 字节，复制少了会把原函数第一条指令的一部分留在 detour 之后当垃圾执行。

### 5.2 必须重定位 rel32

trampoline 是把原指令**搬到另一块内存**。凡是带相对位移的指令
（`E8`/`E9` rel32、`0F 8x` jcc rel32），搬过去后同一个 rel32 指向的就变了。

`sub_4A5AF0` 序言第 2 条就是 `E8 3A FF FF FF`（call `sub_4A5A30`）。
盲搬之后它指向 `stub+6-0xC6`，一块从未分配的内存。

**重定位要按指令边界走查，不能逐字节扫 `0xE8`/`0xE9`**——
立即数或 disp32 里某个字节恰好是 `0xE8` 会被误判，损坏无辜指令。

## 6. GBK 解码与西里尔乱码

### 病根：解码失败时退回单字节

```c
// 错误写法
if (n <= 0 || ch == 0) { ch = (wchar_t)a; return 1; }   // a 是 0x81..0xFE
```

解码失败时把**首字节本身当字符返回**，只消费 1 字节。
该字节随后进入引擎 `sub_4A25E0` 按 `u8` 查表，命中原版字体的
`0xC0-0xFF` 西里尔槽位 → **渲染出一个西里尔字母**。

触发场景：字符串尾部孤立高位字节（`p[1] == 0`）、
或引擎传入的 `len` 切在双字节中间。

**正解**：解码失败返回 0，调用方跳过该字节并计入一个占位宽度，
**绝不把高位字节交给引擎**。

### 第二个坑：`ch >= 0x4E00` 过滤

```c
// 错误写法
if (used == 2 && ch >= 0x4E00) { /* CJK 路径 */ }
else { /* 引擎原路径，按 2 字节分别查表 */ }
```

GBK 里有大量低于 U+4E00 的双字节字符——中文标点。
实测部署的 `english.dat` 里有 4 种共 11 次：
`。`(U+3002)、`、`(U+3001)、`·`(U+00B7)、`“`(U+201C)。

它们掉进 `else` 后被当成两个单字节 → **两个错字/西里尔**。

**正解**：`used == 2` 就走 CJK 路径；atlas 查不到时，
把**原始 2 字节**整体交给引擎，而不是拆开。

## 7. 测宽与绘制的 advance 一致性

`sub_4A2650`（测宽）和 `sub_4A2C50`（绘制）是两个独立 hook，
但**必须用同一份 advance**——`.fff` 条目的 `u16`（记录 +2 偏移）。

| 途径 | 数据来源 | 每字 advance |
|---|---|---|
| 测宽 hook | TTF 栅格化器 | 14 |
| 绘制 hook | `.fff` 条目 adv | 18 |

引擎用测宽结果算起始 x，却用绘制的 advance 排字，每字差几像素，
**误差随字数累积**。用户观察是"两个字还算正常，四个字往左偏得严重"，
与逐字累积的特征完全吻合。

**正解**：测宽改为读取与绘制同一份字形记录
（复用 atlas 的 `GlyphAdvanceOf`，内部走与绘制完全相同的查表路径）。

这也意味着：任何对绘制侧 advance 的修改，必须同步到测宽侧，否则重新引入漂移。

## 8. MSVC 构建约束

VS 2017 / MSVC v141 下的实际约束，都是踩过的：

| 问题 | 现象 | 正解 |
|---|---|---|
| 源码含非 ASCII | C4819 + 一堆虚假"未声明标识符" | **源码保持纯 ASCII**，注释也不用中文（MSVC 按代码页 936 读源） |
| `__thiscall` 用于自由函数 | C3865 | 用 `__fastcall(this, edx_unused, ...)`，对 `__thiscall` ABI 等价 |
| `static` 修饰的 `Log`/`g_font` | 跨编译单元链接失败 | 去掉 `static` |
| `__ImageBase` | 未声明 | 用 DllMain 里保存的 `g_hModule` |
| 同名函数在两个 .cpp 定义 | 重复定义 | 移除多余的一份 |

另外两个部署期约束：

- **`chs_debug.log` 是 ANSI（GBK）编码**。按 UTF-8 读会得到空内容，
  曾据此误判"DLL 没有加载、ASI 位置不对"，实际日志一直在。
  读日志前先确认编码，否则会得出完全错误的结论。
- 覆写 `.asi` 前必须关闭游戏，否则 `PermissionError [WinError 32]`。

## 9. 被证伪的假设

记录这些是为了避免重复劳动。**以下推断都被证据推翻过：**

| 假设 | 推翻证据 |
|---|---|
| 方块 = 每页 200 字形超出 128×128 容量 | 改为 87 页后症状依旧 |
| 方块 = 纹理被销毁（hook `sub_4A5AF0`） | hook 装成功但日志显示从未触发；真凶是另一个调用者 `sub_4A5940` |
| 方块 = 像素值位深不符（1-bit vs 8-bit） | 实测原版与生成的都是 0..255 连续值，无差异 |
| 中文不显示 = ASI 放错目录 | `scripts\` 是正确的；日志是 ANSI，按 UTF-8 读成空导致误判 |
| 末尾字异常 = `english.dat` 被截断 | 手动遍历证明 blob 完整；且 build 与游戏副本 md5 一致。是我自己的检查脚本有 bug |
| ASI 未被加载 = 要移到游戏根目录 | 同上，误判。移过去的文件已移回 |

**方法论教训**：

1. 症状描述里的**变化条件**是最值钱的线索。"越长越偏"直接指向逐字累积的
   advance 不一致；"进 3D 世界才出现"直接限定必有一个随场景切换的状态重置。
2. 静态推断连续两次不中就该停下来做**最小变量实验**或取**运行时数据**，
   不要继续堆假设。
3. **自己的检查脚本也会错**。下"数据被截断"这种结论前，
   要用手工遍历或第二个独立方法复核一遍。
